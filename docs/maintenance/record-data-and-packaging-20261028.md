# 記録データの公開契約と製品JARへの分離 — 2026-10-28

基点: PR #58統合 `eb0bf6a0fa56d35877f332536551361a5de7b996`。
機能実装と個別試験を保存したコミット: `84e453be96f146420170fd541ad65a9293b64493`。
最終headの全体CI・レビュー・統合結果は、この変更のPRに実測結果を記録する。
以前の `record-ui-api-20261027.md` / `feature-ui-v1-boundaries.md` はそれぞれの時点の記録。
「記録画面は本体のまま」「旧CSVの経験値欠落は現行画面でも未解決」という部分は、本変更の範囲で更新される。

## 今回実装した構成

```text
既存CSV・戦闘記録
  → 本体の読取処理
  → RecordDataV1 の変更不能な値・一覧・期間別一覧
  → charts機能JARの記録画面と表示専用モデル

戦闘詳細を開く要求
  → RecordViewsV1（記録日時）
  → 本体の既存詳細読取・描画
```

`RecordDataV1` は戦闘・遠征・開発の読取専用契約。公開メソッドにはJavaFX型、既存の可変bean、
内部のCSV解析クラスを出さない。行はrecord、一覧と期間別Map・その内部Listも変更不能。
読取後に元の可変解析オブジェクトを変更しても、返した値は変化しない。
これは取得後の値の不変性であり、複数ファイルをまたぐ原子的読取や同時追記中の完全性を保証するものではない。
従来の読取処理の不在・不正行に対する方針は維持し、不正行を削除したりデータを補完して保存したりしない。

戦闘集計は `BattleTotals` という変更不能な値を返し、画面が表示用の行へ変換する。
同じ計算を二重実装せず、旧 `BattleLogs.collect` も共通の集計処理へ委譲する。
期間選択は既存の期間判定へ委譲し、今回無関係なリセット規則を変更しない。
遠征画面の従来の直近2か月制限は読取段階で適用し、無関係な古い行を全件snapshot化しない。
公開のexclusive cutoffは同一時刻を別タイムゾーンで指定しても同じ境界になるよう検証する。
開発CSV解析も共通処理へ移し、旧 `CreateItem.parse` はその互換用入口として残す。

## 実際の配布配置

既存の本体＋3機能JAR構成、同一coreハッシュでの更新条件、共有クラスローダーは維持する。
新しい独立JARをむやみに増やさず、記録一覧・集計画面を既存のchartsモジュールへ配置する。

| JAR | この変更後の担当 |
|---|---|
| core | 通信・ログ保存/読取、データ契約の実装、共通状態、詳細戦闘描画、旧プラグイン互換型 |
| calculators | 従来の計算機群 |
| charts | 資材/経験値チャート＋戦闘ログ/遠征ログ/開発ログの3画面、集計期間ダイアログ、表示専用モデル |
| status | 従来の入渠候補/基地航空隊/アイテム一覧 |

登録済み機能IDは7件のまま。既存メニュー・FXML名・ウィンドウ設定キーを変えない。
分割JAR内の画面は従来の10画面に記録3画面を加えた13画面。
記録画面の更新単位はchartsモジュールであり、「記録だけを第4の独立JARとして更新できる」という意味ではない。

### 旧配布形式を維持する追加プロファイル

v2配布manifestに `record_ui_profile: record-ui-in-charts-v1` を追加する。
本体の `RecordDataV1.class` 有無とプロファイルを対応させ、新しい本体では記録画面をchartsに必須とする。
プロファイル削除、未知プロファイル、本体への画面の残存、必要クラス不足、別モジュールへの誤配置を拒否する。
ハッシュを再計算しただけで配置検査を通過できるようにはしない。

同APIを持たない旧本体から作るv2配布は、プロファイルなしの元の配置で引き続き検証できる。
同梱の更新済み検証器・ランチャーを使うことが前提で、過去の検証器が新プロファイルの配置保証まで
認証するとは主張しない。配布生成は新規領域だけに行い、入力JAR・旧配布・旧管理領域を書き換えない。

## 旧APIと既存データ

`BattleLogCollect` / `BattleLogDetail` / `MissionLogCollect` / `MissionLogDetail` の既存公開型は削除しない。
古いバイナリとの互換用に本体に保持し、既存のメソッドシグネチャを変えない。
現行記録画面では新しい表示モデルを使用し、旧可変解析型・旧集計型には直接依存しない。
`MainMenuController` の最新戦闘読取も、画面用行へ変換せず解析済み記録日時を直接使用する。
このため現行の読取・集計経路は整理できたが、旧ABIのための型参照まで完全撤去したわけではない。

### 旧CSVの経験値欠落

14列の旧CSVでは経験値欄がなく、以前の現行画面は `Integer.parseInt("")` で失敗した。
新しい画面では次の3状態を分ける。

| 保存値 | 表示・数値の扱い |
|---|---|
| `0`など正常な整数 | 記録された数値として表示・並び替え |
| 空欄・未記録 | 数値はnull、表示・コピー・グループ名は「未記録」 |
| 数字でない値・整数範囲外 | 数値はnull、表示・コピー・グループ名は「不正」。元の値はsnapshotに保持 |

欠落を0で埋めず、CSVやJSONを書き換えない。現行・旧形式・不正経験値の混在3行を実画面で検証する。
ここで解消したのは組込みの記録画面と最新戦闘への入口。未変更の旧表示型を外部プラグインが直接呼ぶ場合の
独自の振る舞いまで変更・修正したとはしない。

## 検証と証跡

追加Java試験25件: immutable snapshot、可変元の変更からの分離、集計の境界、旧API、
値の未記録/不正/0、日付範囲、既存期間との一致、画面の内部読取依存の禁止など。
以前の公開GUI試験5件と合わせた個別30件は実行・成功済み。
追加Python試験9件で新プロファイルの配置・不正な変更の拒否・旧配置・入力保持を確認し、従来の配置試験8件も成功。

実GUI試験は `build_feature_distribution.py` が生成した本物のcoreとcharts JARを使用する。
テスト専用の架空の配布形式は使わず、本体から対象画面を代替ロードできないことも確認する。
別クラスローダーはテスト上の追加検査であり、製品のクラスローダー方式の変更ではない。
確認内容は次のとおり。

- 戦闘3行（現行/旧14列/不正経験値）、既知の経験値60、未知2行を数値へ捏造しない。
- 遠征2行の燃料75、開発成功/失敗2行、全選択。
- 旧値・不正値の実セル表示、並び替え、3状態別集計、タブ区切りコピー内容。
- 集計期間ダイアログの読込、設定保存と別Configからの再読込。
- 返したList/Map/内部Listの変更拒否、入力JARと全合成履歴のバイト不変。

`verify_r3.sh` はこの実配布GUIの成功と追加24件以上の実行を必須化する。
単にPython試験をスキップしただけ、あるいは本体内の画面へ代替ロードしただけでは全体CIを成功にしない。
合成データのみを使い、Mint・本人データでの検証とはしない。
初期の試験生成・型指定・不正配置fixtureの誤りを含むログは、別tooling枝の
`.maintenance-evidence/record-data-build-v1.json` ～ `v5.json` に保持している。
これらのtoolingと失敗ログは製品ソース差分には混ぜない。
